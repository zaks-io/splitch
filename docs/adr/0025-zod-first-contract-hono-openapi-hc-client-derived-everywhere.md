# Zod-first contract: one authored source, everything else derived; Hono `hc` inside the Control Plane SDK; no committed generated artifacts

**Status:** accepted

## 2026-08-26 amendment: one published SDK dependency spine

The internal authoring split remains accepted: `@splitch/contracts` owns Zod schemas and
`@splitch/control-plane-sdk` owns typed transport. Neither package is published independently.
Their consumer-ready interface is now bundled and declared at `@splitch/sdk/control-plane`.
Published CLI code imports only that interface, so an npm consumer sees
`@splitch/cli -> @splitch/sdk` instead of an implementation bundle with erased workspace edges.

The same rule applies to runtime-neutral local evaluation. `@splitch/evaluation-core` remains a
private implementation package, while `@splitch/sdk/local-evaluation` publishes its evaluator and
the contract-derived types needed by first-party integrations. `@splitch/convex` depends on that
SDK interface and no longer carries a duplicate Resolution Details type.

This amends the earlier "no external/published Control Plane SDK" decision only at the package
interface. There is still no separately versioned `@splitch/control-plane-sdk`, no generated client,
and no second authored contract. The public SDK owns the release compatibility promise and declares
the Hono/Zod runtime dependencies required by its platform subpaths. Its root and browser entries
remain isolated, zod-free data-plane bundles.

ADR-0017 committed "contracts-first OpenAPI/Zod" and ADR-0023 committed a "shared typed client
generated from the contract," but both left the mechanism open: is the _contract_ the OpenAPI doc
(spec-first) or the _Zod schemas_ (code-first)? Is the client codegen'd or type-inferred? Are the
generated artifacts committed? This ADR resolves all three.

**Zod is the single authored source of truth. Everything else is derived.** The control-plane
contract is authored as Zod schemas via `@hono/zod-openapi`. From that one source:

- **TypeScript types** come from `z.infer` (never hand-written).
- **The OpenAPI document** is generated by `@hono/zod-openapi` (never authored).
- **The Control Plane SDK transport layer** uses Hono's `hc` (type-inferred from the server app type; no codegen).
- **MCP tool schemas** are derived from the same Zod route inputs/outputs.
- **Worker request validation** runs the same Zod schemas at the HTTP edge.

There is no second authored representation of any shape anywhere. A glossary noun is one Zod schema,
reused everywhere.

## Decisions

- **Code-first, Zod as source.** Write Zod; infer types; generate OpenAPI. The OpenAPI doc is an
  output, not an input. This matches ADR-0017's Hono-on-Workers choice, where `@hono/zod-openapi` is
  the idiomatic path, and means the schema that _validates_ the Worker boundary (where ADR-0023 says
  all invariants live) is the same schema that produces types and docs.

- **Two packages.** `@splitch/contracts` holds the Zod schemas, `z.infer` types, and the
  `@hono/zod-openapi` route definitions; it is dependency-light (`zod` + `@hono/zod-openapi`).
  `@splitch/control-plane-sdk` depends on `@splitch/contracts` and is the Control Plane SDK. Splitting them keeps the
  pure-schema package free of transport code so the MCP server and the marketing site can depend on
  schemas/types without pulling fetch transport. The deletion test passes: contracts has 4+ real
  consumers (Worker, SDK, CLI/MCP, panel).

- **`@splitch/control-plane-sdk` wraps Hono `hc` — type-inferred, zero codegen.** `hc<AppType>()` infers every
  route's input/output from the server type. A server change that breaks a consumer fails `tsc`
  immediately; the SDK cannot drift from the server by construction. We read ADR-0023's
  "generated from the contract" as "derived from one source"; `hc` satisfies the intent without a
  codegen step.

- **No external/published Control Plane SDK — so no codegen seam is built.** Everything is
  internal: the only consumers (CLI, MCP server, control panel) live in the monorepo and can import
  the server types, so type inference covers 100% of them. OpenAPI exists here for _internal_
  consistency, verification, and agent-friendliness — not for outside consumers. Per the deletion
  test, the OpenAPI→codegen path is not built for a consumer that does not exist. (The public
  **OpenFeature data-plane SDK** is a _different surface_ — it talks to the serving hot path, not the
  control-plane API — and its type/contract story is out of scope for this ADR.)

- **MCP tool schemas are derived from the Zod contract, never hand-written.** Each route's Zod input
  (and output) becomes the MCP tool's `inputSchema`/`outputSchema`. The schema an agent reads to call
  a tool is byte-for-byte the schema the Worker enforces, so an agent never hits a "valid per the
  tool schema, rejected by the server" mismatch. A new endpoint becomes a new MCP tool mechanically
  (ADR-0023's stated goal).

- **Reuse at the leaf, not the envelope.** The shared, reused-everywhere unit is the _leaf_ schema —
  a glossary noun (`Variant`, `TargetingRule`, `Metric`). Request, response, and storage shapes are
  _distinct compositions_ of those leaves, not one fused schema. The Run-immutability invariant
  (ADR-0002/0003) forces this: a create-Run input and a patch-Run input are different shapes (patch
  must reject the frozen assignment-config fields), which a single shared schema cannot express.
  Stored shapes also carry internals (computed timestamps, `runId`, dedup-engine fields per ADR-0024,
  the audit "which door" of ADR-0022) that must not leak onto the wire.

- **Validation: contract edge always; KV reads always; D1 trusts its schema.** Every untrusted-input
  crossing at the Worker HTTP edge is Zod-parsed (non-negotiable — ADR-0023's invariant home). KV is
  schemaless JSON with real version skew, so **every KV read is Zod-parsed, including the
  latency-critical hot-path reads** (Assignment Store and flag config, ADR-0009): a malformed blob
  fails loud rather than flowing a half-valid object into evaluation. D1 has a column schema and
  migrations enforcing structure, so D1 rows are trusted as structurally sound and are not re-parsed.
  (Trade latency for loudness now; optimize later only with a measured reason.)

- **All derived artifacts are build-time, never committed.** Only Zod schemas are authored and live
  in the tree. The OpenAPI doc is served from a Worker route / produced in CI, never a file in the
  repo; MCP schemas derive at build/startup; `hc` and `z.infer` types are compile-time inferences.
  This is deliberate: a committed generated artifact is something agents fight — they hand-edit it,
  regenerate it spuriously, or "fix" a drift-check by editing the generated file instead of the Zod
  source, inverting the source-of-truth discipline. Nothing generated ever lands in the tree.

- **One canonical `ErrorResponse`, extensible by `code`.** A single base error schema
  (`{ code, message, details? }`) with a shared `code` enum is the floor for every endpoint, so every
  consumer (`hc` client, CLI, MCP) has one guaranteed error path. Specific errors _extend_ the base
  (`.extend()` / discriminated union on `code`) to carry typed `details` (e.g. `RUN_FROZEN` with the
  frozen fields and current `runId`) while remaining a member of the base shape. Zod parse failures
  and domain-invariant failures (frozen Run) come back in the _same_ shape. No parallel, unrelated
  error shape exists.

## Considered options

- **Spec-first (author OpenAPI, generate Zod/types via `orval` / `openapi-zod-client`)** — rejected.
  Inverts the source of truth away from the schema that actually validates the Worker boundary, and
  makes the runtime validator a generated artifact rather than the authored one.
- **tRPC (TypeScript-first, OpenAPI as a bolt-on)** — rejected: re-litigates ADR-0017/0023's explicit
  OpenAPI commitment and the Hono choice.
- **One package for contracts + client** — rejected: forces schema-only consumers (marketing site,
  MCP) to pull transport code to get a type.
- **Codegen'd client from the OpenAPI doc now** — rejected: speculative indirection (deletion test)
  for an external consumer that is not planned; `hc` covers every real (internal) consumer with zero
  codegen and stronger drift guarantees.
- **Hand-written MCP tool schemas** — rejected: a second authored copy that drifts from the Worker's
  real validation; the "two ways to do one thing" footgun.
- **One fused schema per entity (contract = type = storage)** — rejected: cannot express the
  create/patch asymmetry the Run invariant demands, and leaks storage internals onto the wire.
- **Skip hot-path KV validation (trust the writer)** — rejected: violates fail-loud for a latency
  shave that should be earned with a measurement, not assumed.
- **Committed OpenAPI doc + CI drift-check** — rejected: a committed generated file is agent busywork
  and a source-of-truth inversion risk; build-time generation removes the artifact agents would fight.
- **Ad-hoc per-endpoint errors** — rejected: agents cannot reliably parse errors, defeating the
  agent-friendly verification goal.

## Consequences

- **No codegen step anywhere in the build.** Types, SDK transport, and (internally) the OpenAPI doc are all
  derived without a generate-to-disk stage. The only authored, committed artifact is Zod.
- **`@splitch/contracts` is the load-bearing shared package** (ADR-0023's "shared typed client" need,
  realized as contract + `hc`). Adding an endpoint propagates to the Worker validator, the client
  types, the OpenAPI surface, and the MCP tool set from one edit.
- **Agent-friendliness is structural, not aspirational:** the tool schema an agent sees equals the
  Worker's enforcement, errors are typed and uniform, and the OpenAPI surface is a generated,
  always-truthful internal map.
- **No glossary impact.** "contract", "leaf schema", "envelope", "error code" are implementation
  vocabulary, not domain language; CONTEXT.md stays a glossary (no new terms).
- **The data-plane OpenFeature SDK contract is unresolved by design** — a separate surface (serving
  hot path, not control plane) to be decided on its own.
